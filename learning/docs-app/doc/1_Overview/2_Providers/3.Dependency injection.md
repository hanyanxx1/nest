# Dependency injection：学习锚点与进度

官方章节：[Providers - Dependency injection](https://docs.nestjs.com/providers#dependency-injection)

## 官方内容讲解

Nest 根据构造函数参数的运行时类型寻找 Provider。默认单例作用域下，容器创建一次实例，并将同一个实例提供给依赖它的类。

TypeScript 的构造函数参数属性（如 `private catsService: CatsService`）会同时声明类成员并保存构造函数实参；Nest 依赖的是 `CatsService` 这个运行时类类型。接口、类型别名和 `import type` 会在编译时被擦除，不能直接作为运行时查找标记。非类依赖需要显式 token 和 `@Inject()`，属于后续 Custom providers 小节。

## 当前实现与已有证据

- [NestFactory](../../@nest/core/nest-factory.ts) 在创建应用时为模块 `providers` 中的每个类创建一个实例并按类存入 Map；创建控制器时读取 `design:paramtypes`，再按类型从 Map 取出实例。
- [provider-injection.e2e-spec.ts](../../test/2_Providers/1_providers/provider-injection.e2e-spec.ts) 已通过，验证 `CatsService` 类类型能够注入控制器。
- [cats-service.e2e-spec.ts](../../test/2_Providers/2_services/cats-service.e2e-spec.ts) 已通过，验证同一注入的服务实例能在 POST 写入后，于后续 GET 返回数据。
- ✅ [provider-singleton-sharing.e2e-spec.ts](../../test/2_Providers/3_dependency_injection/provider-singleton-sharing.e2e-spec.ts) 已通过：写入与读取由两个不同控制器处理，第二个控制器能读取到第一个控制器写入的猫。
- [dto-metadata.e2e-spec.ts](../../test/1_controller/14_request_payloads/dto-metadata.e2e-spec.ts) 已验证方法参数的 class 类型会保留为构造函数，interface 则变成 `Object`；该用例不是构造函数依赖查找测试。
- ✅ [interface-injection.e2e-spec.ts](../../test/2_Providers/3_dependency_injection/interface-injection.e2e-spec.ts) 已通过：构造函数声明 interface 依赖时，初始化阶段因运行时 token `Object` 未登记而失败。
- [Injectable 装饰器](../../@nest/common/decorators/core/injectable.decorator.ts) 会写入 `INJECTABLE_WATERMARK`，但当前 `NestFactory` 的 Provider 注册和查找没有读取该标记。

## `@Injectable()` 标记的作用边界

- 学习版的 `@Injectable()` 当前只写入 `INJECTABLE_WATERMARK`；最小容器从模块 `providers` 数组收集类，并用构造函数的运行时类型查找实例，因此此流程不读取该标记。
- 官方装饰器还会写入作用域元数据；官方 `Scanner` 读取 `INJECTABLE_WATERMARK`，用于阻止把 `@Injectable()` 类误当作模块导入。这个 watermark 不是构造函数依赖的查找 token。
- 官方 DI 仍需结合模块注册、构造函数类型元数据和 Provider wrapper 理解；本学习版尚未实现完整模块扫描及作用域管理。

## 单例共享验证

该用例从应用行为上验证：两个控制器按 `CatsService` 类型取到同一个 Provider 实例；一个控制器写入的数据可由另一个控制器读取。

`@Inject()` 自定义 token 留待 Custom providers 小节。当前测试也不验证 `@Injectable()` 标记是否为注入前提，学习版尚未读取 `INJECTABLE_WATERMARK`。

# Dependency injection：学习锚点与进度

官方章节：[Modules - Dependency injection](https://docs.nestjs.com/modules#dependency-injection)

## 官方内容讲解

Module 类的构造函数可以注入 Provider，例如在模块初始化时读取配置。Module 类本身不应作为其他 Provider 的注入依赖；官方文档提示这会带来循环依赖问题。

## 学习版现状与用例

- [`ModuleContext`](../../../@nest/core/nest-factory.ts) 为每个模块保存独立的 Provider Map，并单独保存 Module 实例。
- [`NestFactory.create()`](../../../@nest/core/nest-factory.ts) 先创建各模块的 Provider 并处理属性注入，再读取 Module 类的构造函数依赖；通过 [`resolveProvider()`](../../../@nest/core/nest-factory.ts) 解析可见 Provider，最后构造并保存 Module 实例。
- [module-class-provider-injection.e2e-spec.ts](../../../test/1_Overview/3_Modules/5_Dependency%20injection/module-class-provider-injection.e2e-spec.ts) 验证 `CatsModule` 的构造函数收到 `providers` 中创建的 `CatsService`，且收到的正是同一实例。用户报告该测试通过（1 个测试）。

## 已验证范围与边界

- 已验证 Module 构造函数可以注入同一模块 `providers` 中的 Provider。
- 实现复用现有依赖解析器，因此也会按模块可见性查找已导出的 Provider；跨模块注入尚未由本节测试单独验证。
- Module 实例保存在 `ModuleContext.moduleInstance`，不放入普通 Provider Map；本节尚未验证 Module 类作为其他 Provider 注入依赖的行为。
- Provider 自身的构造函数依赖、Module 属性注入和 Module 构造函数的可选依赖尚未实现。

其他待补范围：

- `@Optional()` 当前只接入 Controller 构造函数依赖解析；Provider/Module 构造函数和属性注入的可选依赖尚未覆盖。
- 当前依赖 token 以类为主；构造函数显式 `@Inject(token)`、字符串或 `Symbol` token，以及 `useValue`、`useFactory` 等自定义 Provider 形式尚未实现。
- 全局模块、直接 imports/exports 和模块再导出已有独立学习标题；继续时按对应官方内容逐项补充，不在本标题提前展开。

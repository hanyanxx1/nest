# 02. 可复用的源码学习工作流

本文总结一套可以迁移到其他 TypeScript 项目的源码学习方法。目标不只是“能把断点打进源码”，而是建立从使用功能到理解实现、再到自己实现并验证的完整学习循环。

## 学习目标

围绕每个官方文档功能，完成四件事：

1. **会使用**：按官方文档写一个最小示例，理解 API 的输入、输出和使用条件。
2. **看实现**：从示例入口开始单步调试，观察框架源码的调用顺序、关键变量和分支。
3. **自己实现**：在独立的学习目录中写出该功能的最小版本，不覆盖或混入项目正式源码。
4. **做对比**：用相同场景验证自己的实现，并对照官方实现解释行为差异。

这四步组成一个循环，而不是一次性读完整个仓库：

```text
官方文档
  → 最小可运行示例
  → 调试并追踪官方实现
  → 在隔离目录手写最小实现
  → 用相同输入验证并比较
  → 进入下一个功能
```

## 推荐的目录隔离

在学习仓库源码时，尽量让自己的实验和项目正式代码分开：

```text
repository/
  packages/                 # 项目正式源码
  integration/              # 项目正式集成测试
  learning/
    docs-app/               # 按官方文档编写、运行示例
    nest-from-scratch/      # 自己手写的学习实现（逐步建立）
```

目录名称可以按目标项目调整。关键原则是：

- 不把个人练习放进正式源码目录，避免误改或混淆正式实现。
- 不默认把个人练习放进正式测试目录；正式测试可能参与 CI、使用项目约定并有额外维护要求。
- 示例应用和手写实现可以分开。示例负责验证“如何使用项目”，手写目录负责验证“我是否理解并能实现”。
- 不必一开始复制整个仓库的目录结构或实现。只为当前学习的功能建立所需文件，等理解深入后再按职责拆分。

如果项目本身提供容易复用的测试运行器，也可以在 `learning` 中创建自己的测试，并复用该运行器；不必为了“能打断点”而修改正式集成测试。

## 每个功能的具体学习步骤

### 第一步：缩小问题

从官方文档选一个可观察的行为，把问题写成一句话，例如：

> 加上 `@Get()` 后，Nest 如何把控制器方法变成 HTTP 路由？

先定义一个最小输入和可验证结果。避免同时学习多个互相无关的功能，否则断点调用链会很难读。

### 第二步：运行官方用法

在独立示例应用中按照官方文档实现最小例子。先确认应用可以启动，并记录：

- 启动命令；
- 请求或输入；
- 实际输出；
- 预期输出。

这一步先验证 API 用法，不急着修改框架配置或阅读大段源码。

### 第三步：从入口调试官方实现

从应用实际调用的 API 进入源码，而不是一开始就猜某个内部类。以 Nest 为例，可以从 `NestFactory.create()` 开始：

1. 在公开 API 或最靠近它的实现处下断点；
2. 从示例发起一次调用；
3. 按调用顺序单步进入；
4. 只追踪与当前问题有关的分支和变量；
5. 记录“谁调用谁、输入如何变化、结果在哪里被使用”。

如果调用进入第三方库或无关基础设施，可以先跳过；当前目标的调用链足够清楚后再深入。

### 第四步：在隔离目录手写

在 `learning` 下实现一个最小子集，先满足当前例子，不追求兼容完整框架。实现时保持可观察性：

- 每一步都有明确输入和输出；
- 用断点观察关键变量；
- 先实现最短成功路径，再补异常和边界情况；
- 命名和文件职责可以参考官方代码，但不复制与当前目标无关的复杂机制。

例如，学习路由时先让一个控制器方法被映射到一个 HTTP 路径；等这条链路跑通，再考虑参数、守卫、管道等其他机制。

### 第五步：用同一行为验证和比较

尽量用相同的输入分别运行官方实现和自己的实现。比较：

- 返回值或 HTTP 响应是否一致；
- 调用顺序是否相似；
- 官方实现额外处理了哪些情况；
- 自己的实现在哪些输入下会失败。

如果行为不同，先判断是自己实现遗漏、官方 API 语义理解错误，还是官方实现包含了当前练习尚未支持的能力。把差异限制在当前功能范围内，不要因此一次扩展成完整框架。

## 选择运行和调试方式

不同项目的执行链路不同。开始前先回答以下问题：

1. 项目测试或示例由什么工具启动：Node、Vitest、Jest、Vite、专用 CLI，还是其他工具？
2. 实际加载的是 TypeScript、构建后的 JavaScript，还是 bundle？
3. 导入的包名最终解析到哪里：`node_modules`、workspace、本地构建产物，还是源码文件？
4. 若执行构建产物，是否生成 source map，调试器能否找到它？
5. 哪个 `tsconfig` 和 TypeScript 版本负责检查当前文件？
6. 别名配置是否只影响 TypeScript，还是运行时解析也会同步处理？

根据答案选择最少配置的路径：

- **项目已有测试运行器能加载 TypeScript**：优先在 `learning` 下写自己的测试，并复用其测试配置。
- **项目以 JavaScript 构建产物运行**：使用项目自己的构建配置生成 source map，再配置调试器映射。
- **需要模拟真实消费者应用**：建立独立示例应用，让它通过公开包入口加载本地构建包。
- **需要在官方实现与手写实现间切换**：除了 TypeScript 的路径解析，还要确认运行时也会解析到同一份实现；不能只凭 `paths` 能跳转就认定切换成功。

不要把上述方式混为一谈：调试官方实现、让应用加载手写实现、TypeScript 类型解析、Node 运行时模块解析和 source map 映射，是相互关联但不同的事情。

## Nest 项目中的两种模式

### 模式 A：示例应用调试官方实现

当前的 `learning/docs-app` 属于这种模式：

```text
docs-app 使用 @nestjs/core
  → 本地包依赖加载 Nest 构建产物
  → Node 运行 JavaScript
  → source map 将调试位置映射回 Nest TypeScript
```

这适合学习官方文档 API、确认真实应用行为、观察官方 Nest 源码。Nest 源码由仓库自己的工具链构建；示例应用按自己的工具链启动。

### 模式 B：示例调用自己的手写实现

这属于另一种模式：

```text
学习示例
  → 解析到 learning 下的实现
  → 运行并调试自己的 TypeScript 实现
```

可以用路径别名或其他解析机制实现，但要同时验证编译期和运行时解析结果。此模式适合检验自己是否理解了实现，不等于“调试官方源码”。

Nest 仓库的 integration 测试也展示了一个可用的 TypeScript 调试思路：仓库的 Vitest 配置可以把部分 `.js` 导入解析到同名 `.ts` 源文件。不过 integration 是项目正式测试区域；学习者可以参考其配置机制，不必把个人练习直接放在那里。

## 容易混淆的概念

| 概念 | 它回答的问题 | 它本身不保证什么 |
|---|---|---|
| `tsconfig.paths` | TypeScript 检查时去哪里解析导入 | 不保证 Node 运行时按同一别名加载 |
| `package.json` 依赖或 workspace | 应用实际依赖哪个包 | 不保证调试器能显示 TypeScript |
| 编译器或测试运行器 | 如何把 TS 转换或加载为可执行代码 | 不保证加载的是预期那一份源码 |
| source map | 生成代码的位置对应原始源码哪里 | 不会让 Node 直接执行 TS |
| VS Code 调试配置 | 如何启动程序、查找生成代码和映射文件 | 不会自动修复错误的依赖解析 |

调试成功时应分别验证“运行了谁”和“调试器映射到了哪里”，而不是只看编辑器里断点是否变成实心。

## 可迁移到其他项目的启动清单

开始学习一个新源码项目时，按顺序完成以下检查：

1. 找到项目官方文档、最小示例和测试入口。
2. 选一个具体 API 或行为，写出可观测的输入和预期输出。
3. 在独立的学习目录运行最小示例，先确认基线正常。
4. 查清依赖解析和实际加载的文件，不仅凭导入语句或编辑器跳转判断。
5. 查明项目的构建、测试、TypeScript 版本和 `tsconfig`；优先沿用目标项目自己的工具链。
6. 从示例调用点开始调试，沿调用链追踪当前功能。
7. 在独立目录手写当前功能的最小实现，并为它准备可重复的验证方式。
8. 用同一输入比较官方实现和自己的实现，逐步扩展边界情况。
9. 只在确有需要时新增或修改调试配置，并记录它解决的具体问题。
10. 每次修改源码后重新运行或构建，确认加载的是最新代码而非旧产物。

可迁移的是这套**隔离原则、验证顺序和学习循环**，不是 Nest 的某条固定命令或目录结构。换项目时先研究其工具链，再选择最简单、最贴合项目现状的执行方式。

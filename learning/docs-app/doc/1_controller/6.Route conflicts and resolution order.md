# Route conflicts and resolution order：学习用例大纲与进度

官方章节：[Controllers - Route conflicts and resolution order](https://docs.nestjs.com/controllers#route-conflicts-and-resolution-order)

## 官方内容依据

以下内容以你粘贴的官方原文为依据。保留一句关键短引文，其余内容用中文概括：

> “Nest registers routes in declaration order.”

在 Express 这类按注册顺序匹配的适配器中，较早注册的参数路由可能先匹配请求，从而遮蔽后面更具体的路由。例如 `GET /users/:id` 排在 `GET /users/me` 前面时，请求 `/users/me` 会先命中参数路由。应用仍可正常启动，问题只在请求分发时显现；管道无法纠正，因为路由选择发生在管道执行之前。

Nest 提供两个可选配置：

- `routeConflictPolicy` 按冲突类型设置 `off`（默认）、`warn` 或 `error`。`duplicate` 表示 HTTP 方法、路径、host、version 均相同；`shadow` 表示两个路由模式可能匹配同一请求。错误策略会在初始化阶段聚合冲突并抛出 `RouteConflictException`。
- `routeResolutionStrategy` 控制注册顺序。默认 `declaration` 保留声明顺序；`specificity` 按具体程度优先注册字面路径，再注册参数路径，最后注册通配符路径。

冲突策略默认关闭，解析顺序默认按声明顺序，因此既有应用不受影响。策略与适配器有关：Express 受注册顺序影响；Fastify 自身已按具体程度匹配，shadow 检测和 specificity 排序对其无效，但 duplicate 检测仍适用。`RouteConflictPolicy`、`RouteConflictPolicyLevel` 和 `RouteResolutionStrategy` 类型从 `@nestjs/common` 导出。

## 与当前学习实现的关系

当前学习版的 `NestFactory.create()` 已定义 `routeConflictPolicy` 和 `routeResolutionStrategy` 配置类型。`app.init()` 会先收集所有控制器的路由；设置 `duplicate: 'error'` 时，会检查 HTTP 方法、完整路径和 host 均相同的路由；设置 `shadow: 'error'` 时，会检查参数段与字面段的同方法路由重叠。检测发生在路由注册前，默认声明顺序、两种 error 行为，以及多个 duplicate 冲突聚合到同一个初始化异常的行为均已通过测试。`duplicate: 'warn'` 和 `shadow: 'warn'` 已通过 Logger 输出且不阻止初始化；`off` 尚未单独验证，specificity 排序仍未完成。学习版当前只使用 Express，因此本节聚焦 Express 上的行为，不实现 Fastify。

## 日志学习需求与当前进度

学习者希望为学习版已经覆盖的源码路径逐步补充对应日志，包括 `log`、`warn` 和 `error`，并确认是否应使用 Nest 的 Logger 抽象。官方实现中，`NestApplication` 持有带上下文的 `Logger`，初始化完成时通过 `logger.log()` 输出就绪信息；路由冲突检测器接收 logger，并在 `warn` 策略下调用 `logger.warn()`。冲突 `error` 策略则抛出 `RouteConflictException`，检测器本身不直接调用 `logger.error()`。

学习版已实现一个最小 `Logger`，支持带上下文的 `log`、`warn`、`error`，分别输出到对应控制台通道；Logger 单元测试已通过，duplicate 冲突告警也已接入 `Logger.warn()` 并通过集成测试。暂不包含 Nest 官方版本的时间戳、颜色、日志级别过滤和缓冲。后续再逐步为其他已覆盖的源码路径补充日志。

## 用例大纲

### 1. 声明顺序导致的路由遮蔽

- ✅ 声明 `@Get(':id')` 后声明 `@Get('me')`，验证默认行为下 `GET /users/me` 命中参数路由。
- 该用例用于观察冲突在默认配置下会静默发生，而不是应用启动失败。

### 2. 冲突诊断策略

- 验证未配置策略时保持旧行为。
- 分别验证完全重复的路由（duplicate）和可互相匹配的路由模式（shadow）。
- ✅ 验证 `shadow: 'error'` 会在 `app.init()` 注册路由前拒绝参数路由与静态路由冲突。
- ✅ 验证 `duplicate: 'error'` 会在 `app.init()` 注册路由前拒绝完全相同的路由。
- ✅ 验证多组 duplicate 冲突会在同一个初始化异常消息中全部列出。
- ✅ 验证 `duplicate: 'warn'` 通过学习版 `Logger.warn()` 报告冲突并继续初始化。
- ✅ 验证 `shadow: 'warn'` 通过学习版 `Logger.warn()` 报告冲突并继续初始化。
- 验证 `off` 不报告冲突，并保持应用初始化成功。

### 3. 按具体程度解析路由

- 配置 `routeResolutionStrategy: 'specificity'`，验证静态路径优先于参数路径和通配符路径，即使静态路由后声明。
- 验证默认 `declaration` 仍保留原声明顺序。

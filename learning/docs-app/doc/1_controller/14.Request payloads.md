# Request payloads：学习锚点与进度

官方章节：[Controllers - Request payloads](https://docs.nestjs.com/controllers#request-payloads)

## 官方内容依据

以下内容依据你粘贴的官方原文：POST 处理器通过 `@Body()` 接收请求体；DTO 描述网络数据的形状，推荐用 class，因为 class 在运行时仍存在，TypeScript interface 会在编译时被移除。Nest 可借助运行时参数类型元数据获得 class metatype，供 pipes 等功能使用。官方还提示 `ValidationPipe` 可通过 whitelist 去除 DTO 未列出的属性；具体验证行为不在本标题范围。

## 现有覆盖

- `request-data.e2e-spec.ts` 已有 `@Body()` 注入完整 JSON 请求体和 `@Body('name')` 提取指定字段的用例；不重复创建等价测试。
- `schema-metadata.e2e-spec.ts` 已检查 `@Body()` 装饰器保存的参数元数据。
- ✅ `dto-metadata.e2e-spec.ts` 验证 DTO class 在 `design:paramtypes` 中保留为构造函数，interface 则编译为 `Object`；1 项通过。
- ✅ `dto-pipe-metatype.e2e-spec.ts` 先暴露管道缺少类型元数据，加入传递后 1 项通过；管道现可收到 `CreateCatDto`。
- ✅ 原有 `parameter-pipes.e2e-spec.ts`：2 项通过，确认既有 pipe 执行和 schema 元数据传递仍正常。

## 学习版范围

- 本标题关注请求体如何经 JSON 解析、`@Body()` 参数元数据和 resolver 到达控制器，以及 DTO class 为什么能提供运行时类型信息。
- 路由注册时读取方法的 `design:paramtypes` 数组，请求处理时按参数索引将 `metatype` 与 `schema` 一起传给 pipe。
- 官方提示的 ValidationPipe whitelist/剥离未声明属性行为尚未决定是否纳入学习版，完成本标题前需确认是暂缓还是继续实现。
